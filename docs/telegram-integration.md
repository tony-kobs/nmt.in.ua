# Telegram integration: TG-001, TG-002 and TG-003

The webhook-compatible integration uses this boundary:

Telegram -> `/api/telegram/webhook` -> `src/modules/telegram` application service -> existing `src/lib/db/mysql` connection -> MySQL.

Telegram never connects directly to MySQL. The Next.js process does not run a long-lived bot. Only private `/start` messages are handled. Other updates are acknowledged without a reply.

An authenticated user creates a link from `/account`. A 32-byte random token is returned in a Telegram deep link; only its SHA-256 hash is stored. Creating a new link invalidates earlier unused links for that user. The link expires after ten minutes. The webhook validates the secret header, the `/start` payload and Telegram identity, then locks the token and user rows and atomically inserts the unique Telegram account link and consumes the token. Reuse, expiry, a banned user, or an identity already linked to any account fails with a generic user-facing message. Passwords are never sent through Telegram.

The schema is represented by `scripts/sql/035_telegram_account_linking.sql` and is also lazily created by the linking workflow using the existing database pattern. `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, and `TELEGRAM_WEBHOOK_SECRET` are optional: configure them only on the server when enabling Telegram. Without them, `/account` cannot generate a Telegram link and the webhook returns 503; unrelated pages continue working. `.env.example` contains commented placeholders only. When enabled, apply or allow creation of the linking schema and register `https://nmt.in.ua/api/telegram/webhook` with Telegram using the same secret token. Registration is not automated by TG-003. The webhook token must remain server-side. Do not use the production database for local verification.

## TG-003 — read-only Tasks API

`src/modules/telegram/tasks.ts` exports `getLinkedUserByTelegramId(telegramUserId)` and `getTelegramTaskSessions(telegramUserId)`. Both accept a positive safe integer or its canonical decimal string, resolve identity using `user_telegram_accounts.telegram_user_id`, and reject banned accounts. Neither accepts an application user id or authorizes by username. Results are discriminated by `status`, with safe error codes `invalidIdentity`, `notLinked`, and `databaseFailure`. Unknown and banned identities receive the same `notLinked` result; a linked account without current work receives `success` with an empty list. Database failures are logged on the server without returning their context to callers.

The session service resolves the link and reads owned sessions in one parameterized SELECT, so there is no separate identity-resolution/query race. `task_sessions`, `tasks2session`, and `themes` remain the source of truth; mentor assignment tables supply existing scheduling constraints. No schema creation, migration, transaction, or data mutation occurs in this API. Existing migrations (including 033 and 035) must already be provisioned; a missing table produces `databaseFailure` rather than triggering DDL.

Only numeric statuses 2 (created) and 3 (planned) are included. Status 1 (completed), unknown statuses, expired/missing/non-positive deadlines, and rows already considered completed by the session display rule (`tasks_number > 0`, `right_number >= tasks_number`, `time > 0`) are excluded. Expiry is inclusive at `now >= expire_time`, matching `sessionExpiry.ts`. Cancelled mentor assignments, future `available_at` windows, and elapsed `due_at` windows are excluded without changing those sessions. Session types are preserved, including simulator/diagnostic work; a missing theme remains nullable.

Ordering reuses the existing session list's `id DESC` rule. `TELEGRAM_TASK_SESSIONS_LIMIT` is a hard database limit of 50. The small DTO contains only session id/type, theme id/name, numeric status, task count, answered count, and expiry in Unix seconds. Counts use mappings owned by the same linked user; answered includes both correct (1) and incorrect (-1), not unanswered (0). When no mappings exist yet, task count uses the session's planned `tasks_number`. The service never joins the quiz answer bank or exposes answer keys, solutions, auth data, or database rows. It has no dependency on `TELEGRAM_*` configuration and adds no HTTP endpoint or webhook command.

Later increments remain out of scope: TG-004 `/tasks` and `/today`, TG-005 task completion, TG-006 progress, TG-007 notifications, TG-008 reminders, and TG-009 teacher/admin task assignment. The current link is one-to-one; changing or disconnecting it requires a separate authenticated workflow.
