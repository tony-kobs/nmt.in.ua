## Таска 6.1 — Єдиний підручник і коди тем

**Мета.** Залишити поточні конспекти «по класах» (`/materials`, картки зі slug). Додати **загальний підручник** з усіма вже наявними темами: на початку — зміст, клік веде до розділу. Кожній темі дати стабільний **код** у БД, щоб із тесту / результатів / задачника відкривати саме цей розділ.

### Пропозиція

Не плодити другий каталог тем. Джерело правди — таблиця `themes`.

1. Додати унікальний код: `themes.code` (`VARCHAR(32)`, наприклад `ALG-07-EQ`, `GEO-CIRCLE`). Імпорт CSV уже вміє колонки `id,name,description,ord` — розширити схему імпорту опційним `code` (якщо порожньо — згенерувати з `id`: `T-{id}`).
2. У `src/content/learningMaterials` кожному блоку / heading дати `themeCode` або `themeId`. Сторінка підручника збирає всі блоки в один документ і будує TOC з `id="topic-{code}"`.
3. Маршрут: `/materials` лишається сіткою конспектів; нова картка або таб **«Підручник»** веде на `/materials/textbook` (або `#textbook` на тій самій сторінці, якщо контент короткий). Якір: `/materials/textbook#topic-ALG-07-EQ`.
4. У тренажері й на `/results` назва теми — лінк `href=/materials/textbook#topic-{code}`. Стилі лінка: `currentColor`, без нового кольору; kicker / pill як на картках матеріалів.

Класові конспекти **не видаляємо** — це інший зріз (7 / 8 / 9 клас). Підручник — поперечний індекс тих самих тем.

### Кроки

1. SQL: `ALTER TABLE themes ADD COLUMN code VARCHAR(32) NULL UNIQUE` + скрипт `scripts/sql/00x_theme_codes.sql` і бекфіл.
2. Імпорт: колонка `code` в `THEMES_COLUMNS`, валідація унікальності.
3. `getAvailableTopicThemes` / `getTopicResults` віддають `code`.
4. Компонент `TextbookPage`: sticky TOC (на 768+ збоку, на мобільному зверху), секції з `MaterialDocument` / `MathText`.
5. Лінки з `TopicTrainer`, `TopicTrainerSummary`, `TopicResultsTable`.

### Acceptance

- [ ] `/materials` як і раніше показує конспекти по класах.
- [ ] Є сторінка підручника зі змістом; клік скролить до теми (`scroll-margin` під липкий хедер).
- [ ] У `themes` у кожної теми є `code`; з тесту відкривається відповідний розділ.
- [ ] Немає дубляжу тем «Алгебра 7» vs «Рівняння» без коду — одна тема = один код.

## Таски 6.3–6.4 — Самооцінка та вступний тест

**Мета.** На вітальній — кнопка **«Перевір свої знання»**. Спочатку питаємо самооцінку 1–10, зберігаємо її за користувачем. Далі — пробний тест: **по 3 завдання з кожної теми** `themes`. Після фінішу — результат і заклик зареєструватись. Якщо реєструється — ці спроби стають його «Результатами за темами» і «Останніми результатами», самооцінка потрапляє в таблицю результатів. Перед **кожним** новим topic-тестом знову питаємо самооцінку; вона теж іде в рядок теми.

Діагностичний тест з оригінального scope Goldener Rechner.

### Пропозиція

**Самооцінка — окрема таблиця**, не колонка в `task_sessions` (інакше історія змажеться):

```sql
user_self_scores (
  id, user_id NULL, guest_token CHAR(36) NULL,
  theme_id NULL,          -- NULL = загальна оцінка «як я знаю математику»
  score TINYINT NOT NULL, -- 1..10
  source ENUM('diagnostic_overall','pre_topic'),
  created_at
)
```

На `/results` у `TopicResultsTable` нова колонка **«Самооцінка»** (останній `pre_topic` або, якщо не було, загальна). Стиль як `metricNone` / пілюля, не плутати з %.

**Вступний тест**

- Публічний маршрут `/diagnostic` (додати в middleware поруч із `/welcome`).
- Кнопка в `Hero` третім CTA (`btnGhost` або окрема пілюля під основними) + за потреби на `TopicTestStart` для вже увійшлих.
- Крок 1: `ModeTabs` / ряд пілюль 1–10, не слайдер (тап ≥ 44px).
- Крок 2: `startDiagnosticTest()` — `session_type = 5`, по 3 випадкові `quiz_tasks` **з кожної** теми, де є ≥ 3 завдання. Якщо тем багато — ліміт (наприклад max 10 тем × 3 = 30), інакше сесія стане годинною. **Узгодити з ментором**, якщо тем > 10.
- UI: той самий `TopicTrainer` у режимі `diagnostic` (розбір одразу, як звичайний тест).
- Гість: підписаний cookie `nmt_guest` (окремий секрет або той самий `SESSION_SECRET` + інший prefix). Сесія живе на `user_id`, створеному як службовий guest **або** `user_id` nullable + `guest_token` у `task_sessions`. Простіше для поточного коду: тимчасовий рядок в `app_users` (`login = guest_<uuid>`, role student), при реєстрації **перенести** `task_sessions` / `tasks2session` / `user_self_scores` на новий `userId` і видалити guest. Не залишати guest у демо-списку.
- Після фінішу: підсумок + CTA «Зберегти прогрес — зареєструйся» (`/register?from=diagnostic`). `RegisterForm` після успіху викликає `claimGuestProgress()`.
- Увійдений учень теж може пройти діагностику; тоді guest-cookie не потрібен.

**Самооцінка перед кожним тестом**

- У `TopicTestStart` перед `startTopicTestAction`: модалка або крок форми «Як оцінюєш цю тему? 1–10».
- Без оцінки кнопка «Старт» неактивна.
- Пишемо `source = pre_topic` + `theme_id`.

### Acceptance

- [x] З лендінгу гість проходить самооцінку → діагностику → бачить %.
- [x] Після реєстрації ті самі цифри на `/results` і в `RecentResults`.
- [x] Загальна самооцінка збережена; по темах — після кожного старту.
- [x] Таблиця результатів показує колонку самооцінки.
- [x] User A не бачить діагностику user B; guest-cookie не працює як універсальний логін.

### Виконано (`feat/diagnostic-self-score`) — відхилення від пропозиції вище

Реалізовано **не** через тимчасовий рядок в `app_users`, а через підписану cookie
`nmt_guest` (HttpOnly, `SESSION_SECRET`, окремий домен підпису — `src/modules/auth/guestToken.ts`)
+ nullable `guest_token`/`user_id` на `task_sessions`/`tasks2session` + нову таблицю
`user_self_scores` (`scripts/sql/006_diagnostic_ownership.sql`,
`scripts/sql/007_user_self_scores.sql`). Свідоме рішення продукту: службовий
акаунт довелось би ховати з усіх списків користувачів назавжди й він не має
природного «застарівання» — підписана cookie цього уникає.

Уся гостьова/діагностична логіка — в окремому `src/modules/diagnostic/`
(власні owner-aware версії `checkAnswer`/`finishTrainerSession`/`getSessionTasks`/
`markSessionStarted`), щоб жодного рядка в уже протестованому
`src/modules/testing/*` (звичайний topic-test) не чіпати. `session_type = 5` —
одна сесія `task_sessions` на всю діагностичну спробу (`theme_id = NULL`, вона
охоплює кілька тем одразу), не по одній сесії на тему.

`claimGuestProgress()` (`src/modules/diagnostic/claimGuestProgress.ts`) —
атомарний UPDATE трьох таблиць за `guest_token`, викликається з
`registerAction` між `setSessionCookie` і `redirect`; cookie `nmt_guest`
чиститься лише після успішного переносу.

**Нерозв'язане рішення ментора:** якщо тем із ≥3 завданнями більше 10, зараз
беруться перші 10 за `themes.ord ASC, id ASC` (порядок навчального плану) —
детерміновано й тестовано, але саму політику (порядок плану vs. випадкова
підмножина vs. стратифікація за класом) ще треба узгодити з ментором.

**08.09:** самооцінку перед стартом тесту за темою знято з `TopicTestStart`
(лишилась на `/diagnostic`). Кількість завдань учень вписує сам.

### Виконано (`feat/interactive-diagnostic-experience`) — підсумок діагностики й архітектура завдань

Підсумок вступного тесту (`mode="diagnostic"`) тепер окремий компонент

лінки «Результати за темами» / «Мої сесії» — без %-фокусу і без відновлення
колонки «Останні результати» (вона лишається прибраною, див. запис
2026-09-08 у `design-system.mdc`).

Дані для карток тем **не нова таблиця** — `src/modules/diagnostic/diagnosticThemeBreakdown.ts`
рахує correct/total per-theme з тих самих `tasks2session` рядків, приєднаних
до `quiz_tasks.theme_id` (діагностична сесія тем не зберігає — вона на кілька
тем одразу — але кожне завдання в ній усе одно вказує на свою тему). Підсумок
завантажується окремим викликом після finish (`getDiagnosticThemeBreakdownAction`),
за тим самим патерном, що й `getSessionMistakeReviewAction` для Ultimate —
без правок спільного `FinishTrainerSessionActionState`.

Режим `diagnostic` у `TopicTrainer` більше не показує «Вірно» / «Невірно» —
нейтральне «Відповідь збережено» (`resolveAnswerFeedbackKind` /
`resolveAnswerCardState` у `src/modules/testing/answerCardState.ts`, чисті
функції з юніт-тестами). Стандартний topic-test і Ultimate поведінки не
змінили.

**Архітектура інтерактивних завдань** — `src/modules/testing/taskPresentation.ts`
(`resolveTaskPresentation`). Типізовано весь цільовий набір форматів (`choice`,
`visual-choice`, `numeric-line`, `matching`, `ordering`, `error-spotting`,
`fill-gap`, `table-choice`, `expression-builder`), але поточна схема
`quiz_tasks` (текст + 4 фіксовані відповіді, один правильний індекс) реально
підтримує лише два:

- `choice` — як і раніше, плюс опційний **візуал** з `task_text`: якщо текст
  завдання починається з `![alt](url)`, картинку виносить у візуальну зону
  (`TaskVisualArea`), а решту тексту рендерить як звичайне питання. Без нової
  колонки — використовує вже наявне поле `task_text`.
- `table-choice` — якщо `task_text` починається з pipe-таблиці (GFM-стиль:
  `| ... |` + роздільник `| --- |`), таблицю виносить у візуальну зону, а
  текст під нею — питання. Той самий 4-варіантний вибір відповіді.

Решта форматів **лишаються лише типами** — щоб реалізувати їх насправді,
потрібні нові колонки/таблиці (напр. `answer_image_url` для `visual-choice`,
впорядкований список кроків для `ordering`, `matching`-пари, числовий
діапазон + допуск для `numeric-line`). Поки такої схеми немає,
`resolveTaskPresentation` ніколи їх не повертає — небезпечний UI під
неіснуючі дані не пишемо. Коли з'явиться потрібна колонка/таблиця: додати
`case` у `resolveTaskPresentation`, новий варіант `TaskVisual`, і рендерер у
`TaskVisualArea` (або окремий компонент для не-візуальних форматів на кшталт
`ordering`/`matching`).

## Таска 6.5 — Наповнення банку завдань

**Мета.** На кожну тему в `themes` — **30–40** завдань різної складності в `quiz_tasks`. Для ручної перевірки — окремий файл зі всіма новими тестами (питання, варіанти, правильна відповідь, коментар).

Це **контент-таска з імпортом**, не новий рушій. Складність у поточній схемі **немає окремої колонки** — не вигадувати UI фільтра, доки немає поля.

### Пропозиція

1. Спочатку вивантажити живі `themes` (id, name, code) — завдання чіпляти тільки до існуючих `theme_id`.
2. Додати опційно `quiz_tasks.difficulty` `TINYINT` 1–3 (базовий / середній / підвищений) **або** кодувати в `name` префіксом `[1]` / `[2]` / `[3]`, якщо ALTER на хостингу небажаний. Краще колонка: тоді topic-test зможе фільтрувати пізніше. Імпорт — нова колонка в `QUIZ_TASKS_COLUMNS`.
3. Генерація: для кожної теми 30–40 завдань, ~рівномірно 1/2/3, 4 варіанти, `right_answer_n`, короткий `comments`. Формули — у синтаксисі, який уже їсть `MathText` / KaTeX (`$...$`).

## Таска 6.6 — Задачник: друкований тест по темі

**Мета.** `/problems` замість заглушки. Це **не** ще один інтерактивний тренажер (для цього є тест за темою). Це аркуш: обрати тему → таблиця завдань → роздрукувати → дати дітям контрольну.

Еталон **поведінки** (не пікселів): [nmt.science.kh.ua/zadachnyk.php](https://nmt.science.kh.ua/zadachnyk.php).

Закриває стару 3.9 і пункт scope «експорт» (друк / «Зберегти як PDF» з діалогу, без PDF-бібліотеки).

**Окремий банк — так.** Друковані тести ≠ завдання тренажера. `quiz_tasks` уже їдять topic-test і діагностику (`ORDER BY RAND()` без фільтра). Якщо покласти задачник туди ж, контрольна для класу змішається з онлайном. Тому таблиця `problems` (тема + умова + 4 варіанти + ключ + складність), імпорт **опційний** четвертий датасет — порожній `problems` не ламає заливку тем / `quiz_tasks`.

Не копіювати PR #59 як є: там `problems` став обов’язковим, форма/API/тести/SQL не дотягнуті, PR у `main`. Працювати з `feat/...` → PR у `dev`.

### Поведінка (як на еталоні)

1. Селект «Оберіть тему» — теми, у яких є рядки в `problems` (не `getAvailableTopicThemes` з `quiz_tasks`).
2. Компактна **таблиця** всіх `problems` теми: умова (`problem_text`) + чотири варіанти. Формули — `MathText` / KaTeX. Не картки тренажера: на аркуш має лізти багато рядків.
3. Кнопки показу (стан на клієнті, не окремі сторінки):
   - **Сховати відповіді** — лише умова (аркуш «впиши відповідь»).
   - **Показати варіанти відповідей** — умова + 4 варіанти (тест А/Б/В/Г). Це типовий друк для дітей.
   - **Показати/сховати правильні відповіді** — колонка ключа (номер 1–4). За замовчуванням **сховано**. Увімкнути — для викладача (другий прохід друку або перевірка).
4. Кнопка «Друкувати» → `window.print()`. У `@media print` сховати сайдбар, хедер, селект і кнопки; лишити назву теми + таблицю. Папір світлий, тонкі рамки, високий контраст.

На екрані — токени кабінету (не сирий PHP: не `#fff`, не Times як обов’язок). У друку декор (сітка, орби, скло) вимкнути.

Ключ у HTML задачника **можна** тримати й ховати CSS-ом: це генератор аркуша, не сесія з балом. Не писати `task_sessions` і не робити Server Action «перевірити відповідь».

## Таска 6.8 — Банк офіційних варіантів НМТ

**Мета.** Зараз симулятор бере 22 випадкові `quiz_tasks` з усієї бази (`startNmtSimulator`, `ORDER BY RAND()`). Потрібні **реальні варіанти за останні ~3 роки**: список, відмітка «уже пройдено», старт конкретного або випадкового варіанта.

### Пропозиція

Не змішувати офіційний варіант із topic-банком. Окремі таблиці:

```sql
nmt_variants (
  id, year, label,          -- «НМТ 2024, варіант 1»
  source_note,              -- посилання / УЦОЯО, не копірайтний PDF у git
  tasks_number              -- зазвичай 22
)
nmt_variant_tasks (
  variant_id, task_id, ord
)
```

Завдання варіанта — звичайні рядки `quiz_tasks` (можна службова тема `theme_id` = «НМТ» або nullable). `startNmtSimulator({ variantId | 'random' })` набирає `task_id` по `ord`, не RAND по всій таблиці. Випадковий = випадковий **варіант**, не перетасовка чужих тем.

`task_sessions`: додати `nmt_variant_id NULL` (для type 4). На `/simulator` — сітка карток як матеріали: рік, назва, статус «Пройдено 12.05 · 64%» / «Не пройдено», кнопки «Цей варіант» і окремо «Випадковий». Дані: `JOIN task_sessions` де `user_id` + `session_status = 1` + `nmt_variant_id`.

Контент: зібрати відкриті демонстраційні варіанти УЦОЯО / ЗНО-історію за 2023–2025 (лише те, що дозволено викладати як тренажер). Оформити JSON під імпорт + файл рев’ю `docs/content-review/nmt-variants-{date}.md`. Не парсити чужі комерційні банки.

Ctrl+V у симуляторі — як і раніше відкритий пункт PM; можна закрити в тому ж PR дрібним `onPaste.preventDefault()` на полях відповіді, якщо з’являться поля вводу. Для вибору з 4 варіантів сенсу мало.
