# Міграції схеми

Джерело правди — файли в `scripts/sql/`, за алфавітом імені. Журнал застосованих версій — таблиця `schema_migrations` (`version` = ім’я файлу, `applied_at`).

## Команда

```bash
npm run migrate
node scripts/migrate.mjs --check
```

`node scripts/migrate.mjs --check` лише перевіряє, що `mysql2` і `scripts/sql/` відкриваються, і виходить. Базу не чіпає і значення змінних не друкує.

Скрипт `scripts/migrate.mjs` читає `DB_HOST`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` з оточення, інакше з `.env.production`, інакше з `.env.local` (вже задані змінні не перезаписує). Бере `GET_LOCK('nmt_schema')` короткими спробами по 2 с — менше за поріг slow log (5 с) — і між ними чекає в процесі, загалом до 12 хвилин. Довге блокування всередині одного `GET_LOCK` у slow log не потрапляє. Сесію, яка виконує міграцію, не чіпає. Сесію, яка тримає замок без міграції (сон від 20 с або звичайний запит), знімає і пробує знову. Далі застосовує кожен ще не записаний файл і після успіху всього файлу пише версію.

Файл ріжеться на statements з урахуванням лапок (`'`, `"`, `` ` ``), `\'` / подвоєних лапок, коментарів `--` / `#` / `/* */` і директиви `DELIMITER`. Крапка з комою всередині рядка не закінчує statement. Версія пишеться лише після успіху всіх statements файлу, тож зірваний файл виконується знову, а вже записаний — ні.

Повторний запуск нічого не змінює: записаний файл пропускається. Окремий statement, який впирається в уже існуючу таблицю, колонку, індекс або дубль ключа (errno 1050, 1060, 1061, 1022, 1826, 1062, 1091), пропускається. Інша помилка зупиняє файл, версію не записує, деплой не міняє `www`.

Не обгортати файли в транзакцію: DDL у MySQL комітить сам.

## Деплой

`.github/workflows/deploy-hosting.yml` викликає `scripts/deploy-hosting.sh`. На хості, у каталозі нового релізу, після `npm install` і **до** зупинки Node і `mv` у `www` виконується `npm run migrate`. Помилка міграції залишає живий сайт на попередньому релізі.

У tar входять `scripts/migrate.mjs`, `scripts/migrate-sql.mjs`, `scripts/schema-lock.mjs` і `scripts/sql/`. Якщо їх немає в архіві, вивантаження не починається. `mysql2` — production-залежність: на хості її дає копія `node_modules` живого сайту і `npm install --omit=dev`. Скрипт `dotenv` не імпортує. Немає `scripts/migrate.mjs`, `scripts/sql` або `node_modules/mysql2` — staging стирається, `www` лишається попереднім.

Порожня база хостингу цей набір сама не вигадає: старі `ALTER` розраховані на таблиці контенту, які вже були на сервері. Не ігнорувати errno 1146: інакше пропущений `ALTER` записався б як застосований.

Локально ті самі таблиці створює `002_legacy_content_tables.sql` (`CREATE TABLE IF NOT EXISTS` лише для колонок, які пізніші файли змінюють). На проді ім’я `002_legacy_content_tables.sql` уже стоїть у `schema_migrations`, тож деплой цей файл вдруге не виконує і живі таблиці не переписує. Свіжа база без журналу (`npm run db:setup`, див. [LOCAL_DEV.md](./LOCAL_DEV.md)) проганяє `002`, далі `ALTER`, і отримує ту саму форму.

## `ensure*` у запиті

`src/lib/db/schemaGuard.ts`: кожен `ensure*Schema` один раз на процес дивиться, чи всі його версії є в `schema_migrations`. Якщо так — DDL не виконується і замок не береться. Якщо ні — ті самі короткі спроби `GET_LOCK('nmt_schema')`, загалом до 15 с, і стара ідемпотентна міграція. Вкладений `ensure*` не бере другий лок (інакше глухий кут на другому з’єднанні). Зайнятий лок після 15 с — помилка, а не тихий пропуск.

Після першого успішного `npm run migrate` на проді запити більше не роблять `CREATE` / `ALTER`.

## Наступний номер

Перед новим файлом подивись найбільший числовий префікс у `scripts/sql/` на свіжому `dev` (`git pull`). Наступний файл — на один більше, якщо цей номер ніхто не зарезервував. На момент цього опису найбільший у дереві — `073_theme_levels.sql`. Номери `068`–`071` у дереві відсутні і лишаються під інші задачі, тож новий файл поза ними — `074_коротка_назва.sql`. Не бери номер, який уже є у відкритому pull request.

Ім’я, яке вже записане в `schema_migrations`, не змінюй: деплой вважає його застосованим і вдруге не виконає під новою назвою.

Два pull request з одним номером не зливаються мовчки. Перед відкриттям pull request ще раз підтягни `dev`. Якщо номер забрали, перебазуйся і перейменуй лише свій файл, якого ще немає в базі. Перевірка `node scripts/check-sql-numbers.mjs` (її ж ганяє CI на pull request у `dev`) падає на будь-якому новому дублі. Третій файл з номером `032` або `044` теж падає. Дозволені лише дві пари вище.
